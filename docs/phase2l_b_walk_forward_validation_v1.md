## Why Phase 2L-B follows Phase 2L-A

Phase 2K-C labelled exactly one residual candidate — `avg_dollar_volume_21d`, at its
63-session horizon — `KEEP_FOR_MODEL_RESEARCH`. Phase 2L-A then turned that survivor
into a disciplined research protocol: strictly sequential walk-forward folds, an
embargo equal to the forward horizon, a **model-free rank-only baseline to run
first**, explicit pass/fail gates, and end-to-end leakage controls. Phase 2L-A
trained nothing and authorized no model; it routed here.

Phase 2L-B executes that model-free baseline. The order matters: before anyone fits
even a trivial model, the raw signal must demonstrate that it survives genuine
out-of-sample, chronologically-ordered validation windows. If the model-free baseline
does not hold up, no model is built. This phase therefore measures and gates — it
does not model.

## How the folds are constructed

The session calendar is the sorted set of dates that carry a usable cross-sectional
residual rank IC (feature and 63d residual label both finite, enough names). Forward
labels run past the data end, so the last ~63 sessions have no label and fall out of
the calendar — the walk-forward is built only on labeled dates.

Each fold is laid out by index into that calendar:

- **Training block** — the first fold trains on the earliest `min_train_sessions`
  (≥ 252, ~1 trading year). The reported gated scheme is the **expanding** window
  (anchored start, training span grows each fold); the **rolling** window
  (fixed trailing span) training IC is reported alongside for a decay check. Because
  the model-free direction is fixed, the two training schemes change only the
  reported training IC, not the out-of-sample validation metrics.
- **Embargo** — the next `63` sessions (= the forward horizon) are dropped entirely.
- **Validation block** — the following `validation_sessions` (63) sessions are the
  out-of-sample window.
- **Step** — the window advances one full validation block per fold
  (`step_sessions` = 63), so validation windows are non-overlapping.

There is **no random cross-validation** and no shuffling: the validation block is
always chronologically after the training block. Concrete fold boundaries are derived
from the actual calendar, so the number of folds is a property of the data, not a
hard-coded constant.

## How the 63d embargo avoids leakage

The residual label is a forward 63-session return, so consecutive labels overlap
heavily. Without a gap, a training label whose 63-session forward window ends *inside*
the validation block would peek across the boundary. The embargo equal to the horizon
removes exactly that overlap: with the training block ending at calendar index
`t_end − 1`, its forward label ends at `t_end − 1 + 63`, while the first validation
date sits at `t_end + 63` — strictly after. The tests assert this no-overlap property
on every fold.

The other leakage controls are inherited verbatim from the upstream construction:
features (the candidate signal and the residualization controls) are trailing
point-in-time values; the universe is point-in-time; the residualization is fit only
from same-date cross-sections (the label is strictly forward, so no validation-window
information enters any fit); and the gate thresholds are fixed in advance — they are
never tuned on validation results.

## How the model-free rank-only validation works

Nothing is fitted. In each validation window, names are ranked cross-sectionally by
`avg_dollar_volume_21d`. The long/short direction is fixed from the training window
(and matches the Phase 2K-C bullish read) and applied unchanged to validation. Per
window the analyzer measures only out-of-sample residual-label statistics: the
residual rank IC and its information ratio, the top-minus-bottom residual spread, the
top-decile residual hit rate, the long-leg ticker concentration (single-name share
and top-3 share), and a turnover/stability proxy (top-quintile retention across
consecutive dates). Each window also reports `effective_validation_obs`
(validation dates ÷ horizon), the overlap-discounted independent-observation count.

The per-window metrics are then aggregated: the pooled validation per-date IC mean
and median; the fraction of windows whose sign matches the reference direction; a
moving-block bootstrap CI (block length = the horizon) on the pooled validation IC; a
leave-one-fold-out stability check; a market-regime split (SPY-up vs SPY-down forward
windows, and high vs low market volatility); and a degradation check versus the Phase
2K-C full-sample residual IC.

## Fold results and the aggregate result

The per-fold table (`fold_metrics`), the aggregate block (`aggregate_metrics`), and
the gate outcomes (`pass_fail_gates`) are all computed at run time from the data and
recorded in the results JSON — read them from the emitted artifact rather than
assuming a value. The decisive aggregate fields are
`aggregate_metrics.pooled_validation_mean_residual_rank_ic`,
`aggregate_metrics.frac_validation_windows_same_sign`,
`aggregate_metrics.bootstrap_pooled_ic_ci.excludes_zero`,
`aggregate_metrics.leave_one_fold_out.sign_stable`,
`aggregate_metrics.regime_dependent`,
`aggregate_metrics.degradation_vs_phase2k_c.degraded`, and
`aggregate_metrics.total_effective_validation_obs`.

## Did the walk-forward validation pass, fail, or need more data?

The verdict (`recommendation.recommendation`) is one of three values, under a
deliberately conservative rule:

- **`NEED_MORE_DATA`** when there are too few folds or too few effective observations
  after the embargo — the data cannot support a conclusive test regardless of the
  point estimates. On the current ~3-year, ~40-name, single-regime 2023–2026 export
  the labeled calendar yields only a handful of non-overlapping 63-session validation
  blocks after a 63-session embargo, so this conservative outcome is likely and is
  an acceptable, honest result.
- **`WALK_FORWARD_PASS`** only when every gate passes *and* there are enough effective
  observations.
- **`WALK_FORWARD_FAIL`** when enough folds exist but one or more gates fail
  out-of-sample.

Even `WALK_FORWARD_PASS` is **not** a **production edge** and **not** permission to
train or serve a model. It only allows a later, separately gated phase to *design* a
very simple single-feature candidate.

## Why no model candidate is created yet

The Phase 2K-A model-candidate gate stays locked. Phase 2L-B is the model-free
baseline that Phase 2L-A required to run first; clearing it (if it clears) authorizes
*designing* a simple single-feature candidate, not fitting, scoring, serving, or
promoting one. This phase trains nothing, fits nothing, and creates no model
candidate. It asserts no **production edge**.

## What next phase is recommended

`recommended_next_phase` is derived from the verdict:

- **`WALK_FORWARD_PASS`** → **2L-C — Simple Residual Signal Model Candidate Design**:
  design a single-feature monotonic / rank-transform candidate only — no multi-feature
  model, no neural network, no production scoring, no serving integration, no model-v2
  enablement — and still deploy nothing.
- **`WALK_FORWARD_FAIL`** or **`NEED_MORE_DATA`** → **2K-D — Extend Data / Broaden
  Universe Before Model Research**: acquire longer history and a broader point-in-time
  universe and retest, rather than training a model on a thin, single-regime sample.
